## The taxonomy

Every memory carries a type, the same one across CLI, MCP and HTTP. Defaults to `fact`.

| Type | Holds | Example |
| --- | --- | --- |
| `fact` | A stable truth | *the staging database runs on Postgres* |
| `preference` | How you like things done | *prefers pnpm over npm* |
| `episode` | A time-bound event or decision | *shipped the viewer on 2026-07-05* |
| `procedure` | Reusable steps | *to release: bump VERSION, tag, push* |

A database constraint rejects anything else, even if it gets past the API. Choosing well pays off
twice: the viewer filters by type, and the MCP tool description teaches agents the same
definitions, so an agent saving "user prefers tabs" tags it `preference` unprompted.

<Note>
  Recall results can also carry the sentinel type `context`. Those are chunks of ingested files,
  not saved memories, and their `kind` is `context`. You cannot save one. The sentinel exists so a
  single result list can hold both kinds honestly.
</Note>

## Beliefs, not rows

A memory is a **belief with a lineage**. Rows are never mutated in place.

<CardGroup cols={2}>
  <Card title="rootId and version" icon="code-branch">
    `rootId` is the stable identity of the belief, `version` counts up from 1.
  </Card>
  <Card title="Active is current" icon="circle-check">
    The newest active row is the belief. Older ones are stale: kept forever, out of recall, dedup
    and the graph.
  </Card>
  <Card title="Edges agree" icon="link">
    Each step writes a `replaces` edge from child to parent, so history and the graph tell the
    same story.
  </Card>
  <Card title="Validity is temporal" icon="clock">
    `assertedAt` is when a version became the belief. `staleSince` is when it stopped.
  </Card>
</CardGroup>

## What creates a version

| You do | memloom decides | Outcome |
| --- | --- | --- |
| Save the same text again | Content hash matches | `merged`, a no-op |
| Save the same fact, reworded | Classifier says *identical* | `versioned`, old one goes stale |
| Save a fact that can coexist | Classifier says *complementary* | `added`, its own lineage |
| Save a contradiction | Classifier says *contradictory* | `conflict`, both stay active |
| `memloom update <id> <text>` | No classifier, explicit edit | New version, unconditionally |

Resolving a conflict can step a version too: **keep new** and **merge** make the winner continue
the existing lineage, so a settled contradiction lands in that belief's history instead of
orphaning it.

## Walking history

```bash
memloom history 43c1
# * v3  2026-07-10  the staging db runs on Postgres 17
#   v2  2026-07-02  the staging db runs on Postgres 16
#   v1  2026-06-20  staging uses Postgres
```

Any version's id works. The same chain is at `GET /memory/:id/history`, in the viewer's memory
panel, and in the read-only `memory_history` MCP tool.

<Note>
  Agents can read history but not edit a belief. `update` is deliberately a human action in the
  CLI or viewer. Recall never returns stale versions, so old ones cannot shadow the current one.
</Note>
